POST /score: nearest vectors become fit

How the resume vector is compared with opening vectors through Vectorize.

Your win

Explain why the Worker stores vectors in D1 and also upserts them into Vectorize, then connect a Vectorize score to the persisted fit field.

The route and helper

app.post('/score', async (c) => {
  try {
    const n = await scoreSurvivors(c.env)
    return c.json({ scored: n })
  } catch (e) {
    return c.json({ error: e instanceof Error ? e.message : String(e) }, 500)
  }
})

The route delegates all work and turns a missing resume vector or another failure into a JSON 500 response.

const resume = await getVector(env, 'resume')
if (!resume) throw new Error('no resume embedding')

const { results } = await env.APP_DB.prepare(
  "SELECT key, vector FROM vectors WHERE key != 'resume'",
).all()

APP_DB.vectors is the durable record of the vectors. The helper reads the resume separately, reads all opening vectors, parses each JSON string, then builds Vectorize entries.

Vectorize is the search index

await env.VECTORIZE.upsert(entries)
const matches = await env.VECTORIZE.query(resume, {
  topK,
  returnValues: false,
})

upsert inserts or replaces vectors by ID. query asks for the nearest topK vectors to the resume. Each match contains an opening ID and a similarity score. The helper writes that score back to SQL:

fitStmt.bind(Math.round(m.score * 100), m.id)

That conversion makes a model/index score convenient for the application: a fit of 87 is easier to display than a raw decimal. The source of truth for the current displayed score is now openings.fit.

Interpretation

A high fit means the texts are close in the embedding model's space. It does not prove the candidate meets every hard constraint or that the LLM's explanation is correct.
