One folder, one Worker

Everything in worker/ deploys as a single Cloudflare Worker — a serverless function running on Cloudflare's edge network. It has no always-on server; Cloudflare invokes it on demand for HTTP requests, a daily timer, and queued jobs.

The Worker's job: take a candidate's resume and a profile of preferences, then return job openings ranked by how well they match. To do that it reads from and writes to five Cloudflare services. Those connections are called bindings.

The five bindings

  • BOARD_DB (D1) — the source config. A boards table lists each company feed to pull.
  • APP_DB (D1) — the working data. Tables: openings, vectors, profile, state, scans.
  • AI (Workers AI) — one binding, two jobs: embed text into vectors and run an LLM to write reasons.
  • VECTORIZE — the Vectorize index that finds the openings nearest to the resume.
  • SCAN_QUEUE — a Queue that turns "run a full scan" into a background job instead of a slow request.
Why this matters

The split of BOARD_DB (config) from APP_DB (data) is a deliberate design choice: swapping a feed source never touches the openings table. You will see this separation at work in the /boards and /ingest lessons.

The pipeline at a glance

Five stages turn a feed and a resume into a ranked list. Each maps to a lesson later in the course:

  1. Ingest — pull boards, normalize, write openings (lesson 5).
  2. Filter — drop openings that fail the profile (lesson 6).
  3. Embed — turn resume and openings into vectors (lesson 7).
  4. Score — find the resume's nearest openings (lesson 8).
  5. Rank — write a one-line reason for the best (lesson 9).
