Lesson 13 · identity across boundaries

From Clerk session to Worker identity

Trace how a signed-in browser request becomes a verified user key, and where authentication does not yet imply record ownership.

Your win

Explain why the Worker trusts a verified token subject instead of a browser-supplied user ID, and identify which route still lacks record-level ownership filtering.

Two servers, two checks

Clerk provides the app's sign-in session. The app gates its dashboard and asks Clerk for a session token. The Worker independently verifies that token before it handles protected API routes. A successful app-side check is not a substitute for Worker-side verification.

The app gate and sign-in surface

ClerkProvider wraps the app, while clerkMiddleware() makes Clerk session state available on matched requests. The dashboard page still performs its own gate with await auth(); when isAuthenticated is false, it redirects to /sign-in. The sign-in and sign-up pages render Clerk's hosted-instance components. Configure Google as the only offered method in the Clerk instance settings; these components use those settings rather than hard-coding a provider list.

The dashboard calls useAuth().getToken() before requests and sends the token in Authorization. UserButton provides the signed-in account menu and sign-out action. The corresponding client helpers no longer send user_id or ?user=.

Public auth routes with an active session

The sign-in and sign-up routes are public. Each route calls await auth() before it returns its Clerk form. If the browser has an active session, the server redirects to /. Clerk does not render SignIn or SignUp in that request.

const { isAuthenticated } = await auth()

if (isAuthenticated) redirect('/')

Worker verification creates the identity

app.use('*', cors())
app.use('*', async (c, next) => {
  if (c.req.path === '/health') return next()
  const match = c.req.header('Authorization')?.match(/^Bearer\s+(\S+)$/i)
  if (!match) return c.json({ error: 'unauthorized' }, 401)
  const token = await verifyToken(match[1], {
    jwtKey: c.env.CLERK_JWT_KEY,
    authorizedParties: parties,
  })
  if (!token.sub) return c.json({ error: 'unauthorized' }, 401)
  c.set('userId', token.sub)
  await next()
})

CORS precedes authentication so browser preflight can request the Authorization header. Missing or invalid credentials return 401; missing Worker verification configuration returns 503. The allowed-party list constrains which app origins may present the token.

Verified identity is not the same as full resource ownership

GET /state, PUT /state, and GET /openings/ranked use the verified userId; state writes accept only opening_id and status. POST /scan queues the verified subject and ignores any body userId. But GET /scan/:id currently selects by scan ID alone; authentication proves who called, not that the scan belongs to them. Do not treat an opaque scan ID as an ownership check.

Configuration boundary

App setup needs Clerk publishable/secret keys. Worker setup needs the Clerk JWT public key and trusted authorized-party origins. Google provider credentials and redirect URLs live in Clerk settings; see provisioning.

Primary sources

Clerk App Router authentication, Clerk middleware, Clerk sign-in component, and Clerk token verification. For this codebase, see app/src/app/page.tsx, app/src/lib/api.ts, and worker/src/index.ts.
