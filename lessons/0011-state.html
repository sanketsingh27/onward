Your win

Explain the three allowed statuses, how the upsert makes the latest decision win, and how state changes /openings/ranked.

Write a decision

const body = await c.req.json<{
  user_id?: number; opening_id?: string; status?: string
}>()
if (typeof body.user_id !== 'number' || !body.opening_id ||
    !body.status || !isValidStatus(body.status)) {
  return c.json({ error: 'invalid state payload' }, 400)
}
await upsertState(c.env, body.user_id, body.opening_id, body.status)
return c.json({ ok: true })

The route validates shape and membership. isValidStatus is a type guard over exactly saved, applied, and dismissed. Only then does it call the database helper.

INSERT INTO state (user_id, opening_id, status, updated_at)
VALUES (?,?,?,?)
ON CONFLICT(user_id, opening_id)
DO UPDATE SET status=excluded.status, updated_at=excluded.updated_at

The unique pair (user_id, opening_id) means one current state row per user/job. A second decision updates the existing row rather than creating a history row. updated_at records when the current decision changed.

Read a user's state

const userId = Number(c.req.query('user'))
if (!Number.isInteger(userId)) return c.json({ error: 'missing user' }, 400)
return c.json(await listState(c.env, userId))

GET /state?user=1 returns every state row for that user. This can power a saved/applied/dismissed view independently from the ranked feed.

State feeds back into ranking

The connection is in GET /openings/ranked: its SQL excludes opening IDs where that user's state is applied or dismissed. saved remains visible. The matcher produces candidates; state records the human's response; the next read respects that response.

Domain boundary

fit describes system-generated relevance. status describes a user's decision. Keeping them in separate columns lets a user dismiss a high-fit job without corrupting the model score.

Primary source

Route reference: state endpoints, paired with src/state/state.ts. The SQL upsert is the authoritative behavior.
