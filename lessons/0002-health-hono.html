GET /health: your first request

How a request reaches Hono, receives a context, and becomes JSON.

Your win

Trace GET /health from the browser to c.json({ ok: true }), and explain why c.env is where Cloudflare bindings live.

What handles the request?

Cloudflare invokes the exported object's fetch function for an HTTP request. This code gives Hono that function:

const app = new Hono<{ Bindings: Env }>()
app.use('*', cors())

export default {
  fetch: app.fetch,
  // queue and scheduled handlers come later
}

Hono is a small router. The generic parameter tells TypeScript that every Hono context has an env shaped like Env from src/env.ts. At runtime, Cloudflare supplies those bindings; TypeScript only checks that we use their names correctly.

Route matching

app.get('/health', (c) => c.json({ ok: true }))

Read this as: “when the method is GET and the path is /health, call this function.” Hono passes one argument, c, the request context. It contains the request, URL parameters, environment bindings, and response helpers.

  • c.req — read query parameters, path parameters, headers, and the body.
  • c.env — access BOARD_DB, APP_DB, AI, VECTORIZE, and SCAN_QUEUE.
  • c.json(value) — serialize a JavaScript value and set the JSON response headers.

Middleware runs before the route

app.use('*', cors())

The * pattern applies CORS middleware to every path. That lets a browser frontend hosted on another origin call this Worker. The health handler itself does not know or care about CORS; middleware keeps that cross-cutting concern outside each route.

Design signal

/health deliberately touches no database or model. It answers one narrow operational question: “is the HTTP Worker reachable?” A successful health response does not prove that D1, AI, Vectorize, or the queue are healthy.
