# Assess Resume-vector lookup and 1,000 concurrent scans

## Context
The user asks whether a D1 database lets only one user's Resume vector be read at once, and whether a temporary cache should feed Vectorize during scans instead. Answer directly in beginner-friendly, ADHD-friendly language; correct the conflation between a database processing one query at a time and allowing only one person to scan. State that the existing D1 row already caches the vector until its Resume changes; no code changes or new caching layer are requested.

## Approach
1. Correct the premise with a concrete A/B example: `worker/src/embed/embed.ts:getOrCreateResumeEmbedding(env: Env, userId: string, resume: string): Promise<number[]>` looks up a single `user_id` primary-key row (`migrations/0006_resume_embeddings.sql`) for each scan. A single D1 database handles individual SQL queries serially and can queue many callers; it does not forbid A and B from running scans at the same time or restrict stored data to one user. Cite https://developers.cloudflare.com/d1/platform/limits/ for that distinction.
2. Trace one scan end-to-end in `worker/src/routes/scans.ts` (HTTP request enqueues the job), `worker/src/index.ts` (queue consumer handles messages sequentially within each batch), `worker/src/scan/scan.ts:runScan`, and `worker/src/ingest/ingest.ts:ingestBoards`. Report the concrete scaling hazards: every scan fetches and rewrites shared boards/openings, reads every opening, deletes the shared `vectors` table, re-embeds eligible openings, upserts those vectors to D1 and Vectorize, queries Vectorize, and generates reasons for up to 10 results. The shared delete and board replacement can race between scans; queueing does not guarantee a single global scan at a time. `worker/src/vector/vector.ts:scoreSurvivors` also reads all D1 vectors and re-upserts them when called via `/score`.
3. Explain what is already cached: D1 persistently stores the user-specific Resume vector as JSON text and its Resume-text hash. On unchanged text, the code reads the existing vector and sends it straight to `worker/src/vector/vector.ts:queryVector`, which searches opening vectors in Vectorize without saving a second Resume copy. On changed text or no row, Workers AI creates the vector and the D1 row is updated. Contrast a temporary in-memory cache (not reliable across separate Worker instances or future scans) and a time-limited shared cache (requires expiration/refresh logic) with the current hash-checked persistent D1 cache; no need to add one just to avoid a cheap indexed read.
4. Clarify the actual scalability concern: `worker/src/scan/scan.ts:runScan` and `worker/src/ingest/ingest.ts:ingestBoards` repeatedly re-fetch, rewrite, delete and re-embed shared job data on each scan; `DELETE FROM vectors` can interfere with other scans. If suggesting an optimization, reuse the shared job data/embeddings and remove the shared delete first; do not claim an extra Resume cache fixes the heavy work or prove a 1,000-scan capacity without measurement.

## Verification
- From the repository root with Node 25+, run `node --test test/scan-resume-embedding.test.ts` to verify that two different users have separate Resume vectors, unchanged text reuses a saved vector, changing one Resume embeds only that user's new text, and the legacy shared `vectors['resume']` row is absent. This proves cache behavior, not concurrent capacity.
- Trace a concrete overlap: user A and user B both enqueue `/scan`; each queue consumer can reach `runScan` and its unscoped `DELETE FROM vectors`, and each scan re-ingests the same board rows. Expected conclusion: the code has no cross-scan isolation for these shared writes, independent of distinct D1 Resume rows. No local test or reading of published limits alone proves 1,000-scan throughput; a real load test against a permitted staging deployment is required before giving a number.

## Assumptions & contingencies
- Treat “1,000 concurrent users” as potentially 1,000 simultaneous scans, and explicitly contrast it with 1,000 registered users. Do not assume access to a staging environment or production metrics; if absent, answer qualitatively and label capacity unmeasured.
